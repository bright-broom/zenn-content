「約 142,000 トークンが、約 70 トークンになった」。数字だけを見れば、AI コードレビューの前提が変わるほどの効果に見えます。

しかし、コードが 2000 分の 1 に圧縮されたわけではありません。実際に起きているのは、**ソース全文を AI に渡す前に、ローカルの索引で読む候補を選別すること**です。大きく減るのは主に最初の入力であり、追加のソース参照、回答精度、インデックス運用まで含めた総コストではありません。

![大量のコードから関係グラフを通じて少数の根拠候補を選び、AI へ渡す流れ](/images/code-knowledge-graph-ai-review/00-hero.png =900x)
*コード知識グラフが行うのは、コードの魔法の圧縮ではなく、根拠候補の選別と追跡です。*

この記事では、「なぜ削減できるのか」「約 70 トークンは何を数えているのか」「どこで見逃しが起きるのか」を実装と公開評価から分解します。検証用プロジェクトでは 4 製品を一括導入せず、まず `Serena` とグラフ製品 1 つを読み取り用途に限定して比較するのが妥当です。

## 先に結論

| 読者の疑問 | 回答 |
|---|---|
| コード知識グラフでトークンを削減できるか | 初期コンテキストを削減できる可能性はある。ただし、削減率は比較基準と変更内容に依存する |
| 「2000 分の 1」は再現可能な一般効果か | 未証明。6 コミット中の最大ケースから作られた値で、総トークン数やレビュー精度は測定されていない |
| 知識グラフで AI の推測をなくせるか | なくせない。推測する対象を絞り、影響候補を提示する仕組みと考えるべき |
| Security Scanner の代わりになるか | ならない。独立した静的解析、テスト、実行時検証が必要 |
| 検証用プロジェクトに導入すべきか | 限定的な比較検証は推奨。ただし、4 製品の一括導入は非推奨 |

## コード知識グラフは、なぜ AI のトークンを削減できるのか

先に結論を書くと、コード知識グラフが減らしているのは、コード自体の情報量ではありません。

**ソースコード全文を AI に渡す前に、ローカルの索引で関連候補を選別し、最初の入力をシンボル名、位置、関係、件数へ置き換えることで削減しています。**

したがって、この仕組みは「高圧縮」ではなく、より正確には「検索によるコンテキスト選別」です。

```text
全文を読む方式
質問 → ファイルを検索 → 関連しそうなファイル全文 → AI

構造検索を使う方式
事前解析 → 質問や差分から候補を特定
→ シンボル名・位置・関係だけを AI へ渡す
→ 必要な本文だけを追加取得
```

削減効果は、次の 2 段階から発生します。

1. **選別**：AI へ渡すファイルやシンボルの数を減らす  
2. **表現変換**：ソース本文を、短い構造情報へ置き換える  

![全文を先に渡す方式と、構造検索で候補を選別してから渡す方式の比較](/images/code-knowledge-graph-ai-review/01-context-selection.png =900x)
*図 1：削減の中心は、本文を要約することではなく、最初に渡す本文そのものを減らすことです。*

### 1. ソースコードを事前に索引化する

`code-review-graph` は、Tree-sitter でコードを構文解析し、ファイル、クラス、関数、テストなどをノードとして登録します。

さらに、呼び出し、import、継承、実装、参照、テスト対象などをエッジとして保存します。[parser.py（v2.3.7）](https://github.com/tirth8205/code-review-graph/blob/v2.3.7/code_review_graph/parser.py#L2057-L2400)

```text
Function: verifyToken
├─ CALLS → decodeToken
├─ CALLED_BY → authenticate
├─ REFERENCES → AuthConfig
└─ TESTED_BY → verifyToken.test
```

この構造化処理は、AI に質問する前にローカルで実行されます。

そのため、質問のたびにソース全文を AI へ送らなくても、まず索引から関係する関数やファイルを検索できます。

### 2. Git 差分を関数やクラスへ対応付ける

pre-commit のレビューでは、`git diff` から変更されたファイルと行番号を取得します。

次に、変更行をグラフ内の関数やクラスへ対応付けます。例えば、150 行目の変更が `verifyToken` 関数内にあれば、ファイル全体ではなく `verifyToken` が探索の起点になります。[changes.py（v2.3.7）](https://github.com/tirth8205/code-review-graph/blob/v2.3.7/code_review_graph/changes.py#L381-L529)

これにより、数千行あるファイルでも、最初に確認する対象を関数単位まで狭められます。

### 3. 起点から近い関係だけを探索する

変更されたシンボルを起点として、呼び出し元、依存先、継承関係、関連テストなどを探索します。

`code-review-graph` の影響範囲探索は、既定では深さ 2 の範囲です。リポジトリ全体を返すのではなく、変更箇所から数ホップ以内にあるノードだけを影響候補として取得します。

このとき、AI への入力サイズは、リポジトリ全体の大きさではなく、主に次の条件で決まります。

- 起点となるシンボル数
- 探索する深さ
- 各ノードの接続数
- 返却件数の上限
- ソース本文を含めるか

ただし、接続数の多い共通関数や基盤モジュールを起点にすると、深さ 2 でも候補数が急増します。探索深度を制限すれば常に小さくなるわけではありません。

### 4. ソース本文を返さず、短い構造情報を返す

トークン削減へ最も強く作用しているのが、ソース本文の除外です。

`code-review-graph` の最小出力では、既定で `include_source=False` となり、主に次の情報だけを返します。[review.py（v2.3.7）](https://github.com/tirth8205/code-review-graph/blob/v2.3.7/code_review_graph/tools/review.py#L356-L473)

- 変更ファイル数
- 変更された関数やクラス
- 影響を受けるフロー
- テストが見つからないシンボル
- リスクスコア
- 優先して確認する項目

例えば、変更ファイルの本文が 50,000 文字あっても、最初の結果が次のような短い JSON なら、AI へ送る文字数は大幅に減ります。

```json
{
  "changed_files": 2,
  "changed_functions": 3,
  "affected_flows": 1,
  "test_gaps": 1,
  "risk": "medium"
}
```

つまり、50,000 文字を意味的に数百文字へ圧縮したのではありません。

**最初の段階では本文を送らず、本文の所在と関係だけを送っています。**

### 5. 質問に合った索引から上位候補だけを返す

各ツールは、異なる方法で候補を絞ります。

| ツール | 選別方法 | 主に返す情報 |
|---|---|---|
| `code-review-graph` | Git 差分をグラフノードへ対応付け、近傍を探索 | 変更シンボル、影響候補、リスク、テスト不足 |
| `better-code-review-graph` | シンボル情報と質問のベクトル類似度を比較 | 類似するシンボルと位置 |
| Serena | Language Server で定義、参照、実装を検索 | シンボル名、ファイル、行番号 |
| Graphify | 質問から起点ノードを選び、周辺グラフを探索 | ノード、関係、出典位置 |

`better-code-review-graph` は、シンボル名、種類、親、引数、戻り値などを埋め込みへ変換します。質問との類似度を計算し、上位候補だけを返します。[embeddings.py（v3.21.0）](https://github.com/n24q02m/better-code-review-graph/blob/v3.21.0/src/better_code_review_graph/embeddings.py#L579-L802)

Serena も、シンボル検索では既定で本文を含めません。Language Server が持つ定義・参照情報から、該当するファイルと行番号を返します。[symbol_tools.py（v1.6.0）](https://github.com/oraios/serena/blob/v1.6.0/src/serena/tools/symbol_tools.py#L132-L388)

Graphify は、質問に合う少数の起点ノードを選び、既定では深さ 2 の範囲を探索します。出力文字数にも上限があるため、グラフ全体がそのまま AI へ渡るわけではありません。[serve.py（v0.9.28）](https://github.com/Graphify-Labs/graphify/blob/v0.9.28/graphify/serve.py#L740-L985)

### 「約 70 トークン」の正体

`code-review-graph v2.3.7` の Token Savings 表示は、既定では Claude の実トークナイザーによる測定ではありません。

実装上の計算は、概ね次のとおりです。

```text
比較元
変更ファイルのバイト数 ÷ 4

比較先
構造化された解析結果の JSON 文字数 ÷ 4
```

この計算方法は [`context_savings.py`](https://github.com/tirth8205/code-review-graph/blob/v2.3.7/code_review_graph/context_savings.py#L13-L82) で確認できます。

`--brief` の出力は、ソース本文を含まない固定形に近いデータです。そのため、変更ファイルが 10,000 文字でも 100,000 文字でも、返す件数やシンボル名が同程度なら、グラフ側の推定値はほとんど変わりません。

例えば、同じ計算式で約 275 文字の構造化結果を評価すると、推定値は次のようになります。

```text
275 文字 ÷ 4 = 68.75
```

切り上げると約 69 トークンです。

![約 70 トークンという表示値が、変更ファイルのバイト数と構造化 JSON の文字数を 4 で割った概算比較であることを示す図](/images/code-knowledge-graph-ai-review/02-seventy-token-anatomy.png =900x)
*図 2：「約 70 トークン」は構造化結果の概算値で、レビュー完了までの総トークン数ではありません。*

したがって、複数のコミットで約 70 トークンが続く現象は、次の 2 点で説明できます。

- ソース本文を含まない固定形に近い出力
- `4 文字＝1 トークン` という概算

これは「高度な意味圧縮によって 70 トークンになった」という証拠ではありません。

また、`--verify` を付けた場合も、使用されるのは既定で `cl100k_base` です。Claude 固有のトークナイザーによる実測とは限りません。

再現用リポジトリの現在の README でも、関数名によって出力長が変わることと、Token Savings パネルをそのまま信用しないことが明記されています。[claude-cartography README](https://github.com/shumatsumonobu/claude-cartography/blob/main/README.md#L651-L655)

記事で使用された 6 コミットの生出力は十分に公開されていないため、すべてが正確に 70 となった個別原因は要確認です。

### 削減されたトークンは、どこへ移ったのか

初期入力から除外された情報が、消滅したわけではありません。

レビューを完了するために詳細が必要になれば、AI は該当する関数、呼び出し元、テスト、設定ファイルなどを追加で取得します。

そのため、評価では次のコストを分ける必要があります。

#### モデルへ投入するトークン

- 最初の構造検索結果
- 追加で取得したソース本文
- 再検索結果
- 会話履歴
- モデルの回答出力

#### システム側の処理コスト

- 構文解析
- グラフの構築と更新
- 埋め込みの生成
- SQLite やベクトル索引の保存
- Git Hook の待ち時間
- インデックス障害からの復旧

構造検索が大きく削減するのは、主に最初のモデル入力です。

最初の全文読みが総コストの大部分を占める場合は効果が大きくなります。一方、追加のソース参照、テスト、推論、回答生成が大部分を占める場合、レビュー全体の削減率は小さくなります。

### トークン削減と検索精度はトレードオフになる

返す候補数や探索深度を小さくすれば、入力トークンは減ります。しかし、影響候補の見逃しは増える可能性があります。

特に、次の関係は静的なグラフから漏れることがあります。

- 動的 import
- Dependency Injection
- リフレクション
- 設定ファイルによる接続
- SQL やストアドプロシージャ
- イベントやメッセージキュー
- 生成コード
- Feature Flag
- 外部サービスとの連携

古いインデックスや、質問とシンボル名の意味が合わない場合も、必要なノードが検索上位へ出ない可能性があります。

![返す候補数と探索深度を増やすと、モデル入力トークンと検索再現率がともに増える傾向を示す概念図](/images/code-knowledge-graph-ai-review/03-token-recall-tradeoff.png =900x)
*図 3：狙うべきは最小トークンではなく、必要な影響候補を取りこぼさない最小範囲です。曲線は概念図であり、実測値ではありません。*

したがって、グラフ検索の結果は「影響範囲の確定」ではなく、**限られたトークン予算で優先的に読む候補**として扱うのが妥当です。

### 正しく効果を測る方法

記事の Token Savings 表示は、変更ファイル全文と最初の構造化結果を比較したマイクロベンチマークです。

同じ品質のレビューを、どれだけ少ないコストで完了できたかを示すには、少なくとも次を測る必要があります。

- 最初から回答完了までの総入力トークン数
- 回答出力を含む総トークン数
- 追加検索とソース参照の回数
- 影響ファイルの再現率
- 誤検出率
- 最終回答の正確性
- p50／p95 の所要時間
- インデックスの作成・更新時間
- 検索漏れによるやり直し率

比較対象も「リポジトリ全体を読む方法」だけでは不十分です。

現実的な基準として、全文検索、Language Server、差分ファイルの選択的な読み取り、既存テストを組み合わせたレビューと比較する必要があります。

## 結論

コード知識グラフによるトークン削減の本質は、圧縮ではなく、**事前計算した構造を使って AI が読む範囲を狭めること**です。

```text
事前に構造化する
→ 質問や差分から候補を選ぶ
→ 本文ではなく位置と関係を返す
→ 必要な本文だけを後から読む
```

この設計は、巨大なファイルを最初から読む無駄を減らす方法として有用です。

一方、「約 70 トークン」や「2000 分の 1」は、限定された比較式による初期コンテキストの推定値です。レビュー精度を維持したまま、全処理のトークン数を同じ割合で削減できることまでは示していません。

## 知識グラフは AI の推測を消せるのか

### 直接回答

知識グラフは AI の推測を消しません。検索対象を構造的に絞り、推測の範囲を狭めます。

### 根拠

Graphify は、関係性を次のように分類しています。

- `EXTRACTED`：ソースから明示的に抽出した関係
- `INFERRED`：解決処理によって推定した関係
- `AMBIGUOUS`：確定できない関係

つまり、製品自身が推定された関係を区別しており、すべての辺が確定事実であるとはしていません。[Graphify の Confidence tag](https://github.com/Graphify-Labs/graphify)

`Serena` も、標準の Language Server backend では、外部依存関係にある宣言を取得できない場合があり、実装検索は対象言語の Language Server 機能に制約されると説明しています。[Serena の Retrieval 機能と制約](https://github.com/oraios/serena)

静的解析では、次のような関係が漏れる可能性があります。

- 動的 import
- DI
- リフレクション
- 設定ファイルを介した接続
- SQL
- イベント駆動の処理
- 生成コード
- Feature Flag
- 外部サービスや外部リポジトリの依存関係

インデックスが古い場合は、現在のコードと整合しない結果が、もっともらしい形で返される可能性もあります。Graphify の公式手順でも、更新直後の情報が見つからない場合は、先にインデックスを更新するよう案内されています。[Graphify の更新手順](https://github.com/Graphify-Labs/graphify)

![静的グラフが捉えやすい関数、import、型、参照、継承、テストの外側に、動的 import、DI、設定、SQL、イベント、外部サービス、生成コード、古いインデックスが残ることを示す図](/images/code-knowledge-graph-ai-review/04-static-graph-blind-spots.png =900x)
*図 4：静的グラフの外側に残る関係は、型検査、テスト、実行時検証で補う必要があります。*

**判定：グラフ検索の結果は「影響候補」です。影響範囲の確定には、型検査、アーキテクチャテスト、結合テスト、実行時検証が必要です。**

## 企業リポジトリへ安全に導入できるか

### 直接回答

安全性を確認せず、記事の構成をそのまま企業リポジトリへ導入することは推奨できません。

記事のセットアップでは、複数の Python パッケージ、MCP サーバー、Claude Code の設定、Git Hook をまとめて導入します。[記事のセットアップ](https://zenn.dev/helloworld/articles/bcaea69f58eae5)

トップレベルのバージョンを固定しても、推移的依存関係や取得した配布物の完全性まで自動的に保証されるわけではありません。企業利用では、依存関係、権限、外部通信、生成物、更新経路を個別に確認する必要があります。

### Graphify の外部送信範囲

Graphify のコード解析は Tree-sitter を使用し、コードだけであればローカルで実行できます。一方、文書、PDF、画像の意味抽出には、IDE で利用中のモデルまたは設定した API を使用します。

機密情報を含む可能性がある場合は、`--code-only` で文書や画像を対象外にするか、送信先、保存条件、契約上の取り扱いを確認する必要があります。[Graphify のデータ処理範囲](https://github.com/Graphify-Labs/graphify)

### Security Scanner の検出力

記事と再現用リポジトリでは、意図的に埋め込んだ SQL Injection、ハードコードされた Secret、`eval()` の 3 件を、Security Scan が検出できなかったと報告しています。[claude-cartography の検証結果](https://github.com/shumatsumonobu/claude-cartography)

現在の `better-code-review-graph` の公開仕様では、既定の heuristic engine は 5 個の正規表現ルールで構成され、Semgrep は追加機能として提供されています。これは記事の検証時点から実装が変化している可能性があるため、採用時には固定したバージョンで再検証が必要です。[better-code-review-graph の Security 仕様](https://github.com/n24q02m/better-code-review-graph)

いずれの場合も、コード知識グラフの Security 機能を独立した Security Scanner の代替にはできません。

### 最低限必要な対策

- 隔離された仮想環境で実行する
- 直接依存と推移的依存をロックする
- MCP ツールを許可リスト化する
- 初期検証では読み取りツールだけを許可する
- 外部通信を無効化するか、送信対象と送信先を確認する
- Git Hook を自動導入せず、処理内容と失敗時の挙動を確認する
- Semgrep などの独立した Security Scanner を CI で実行する
- 導入前後の設定差分とロールバック手順を記録する

## 9 問のツール選択テストで何が分かるか

### 直接回答

9 問すべてで意図したツールが選択された結果は、ルーティング規則が機能したことを示します。ただし、最終回答が正しかったことまでは証明しません。

再現用リポジトリでは、ツール名を指定しない 9 種類の質問について、実際の `tool_use` Log から選択結果を記録しています。[claude-cartography のルーティング検証](https://github.com/shumatsumonobu/claude-cartography)

この検証から確認できるのは、質問の種類に応じて期待したツールが呼び出されたことです。次の項目は別途測定する必要があります。

- 最終回答の正確性
- 影響ファイルの再現率
- 誤検出率
- 根拠のない断定の発生率
- モデルや試行ごとのばらつき
- 追加参照を含む総トークン数
- 回答完了までの待ち時間

**判定：ルーティング精度と回答精度は、別の評価項目です。**

## 記事から取り入れるべき設計

記事から取り入れる価値があるのは、4 製品の組み合わせそのものではなく、次の探索設計です。

1. 質問の種類を判定する
2. 全文検索、意味検索、LSP、グラフ検索を使い分ける
3. 巨大なファイルを読む前に、構造化された候補を取得する
4. 候補の根拠となるソースを確認する
5. 型検査、テスト、実行時検証で結果を確定する
6. インデックスの鮮度を確認する

この順序であれば、AI へ渡す情報を抑えながら、グラフ検索だけに依存することを防げます。

## 検証用プロジェクトでは何を導入すべきか

### 1. Serena を読み取り専用で試す

TypeScript のシンボル、定義元、参照先、実装候補の探索に限定します。

初期段階では、リネーム、シンボル置換、ファイル編集などの変更機能を許可しません。

### 2. グラフ製品は 1 つだけ選ぶ

目的に応じて、次のように選択します。

| 主な目的 | 比較候補 |
|---|---|
| コード変更のレビューコンテキストと影響候補の取得 | `code-review-graph` |
| コードと設計書を横断した探索 | Graphify |

両方を同時に導入すると、検索結果、更新処理、障害原因を切り分けにくくなります。

### 3. Git Hook は後から判断する

初期検証では手動でインデックスを更新し、次を確認します。

- 初回構築時間
- 差分更新時間
- 生成・変更されるファイル
- リポジトリサイズへの影響
- インデックス不整合の検知方法
- 更新失敗時の復旧方法
- 完全に削除する手順

### 4. 実案件のタスクで比較する

現行の全文検索、TypeScript Language Service、既存テストを Baseline とし、30 件程度の変更影響調査で比較します。

評価単位は「ツールが呼ばれたか」ではなく、「根拠付きの最終回答が正しかったか」です。

![30 件程度の変更影響調査を固定し、Baseline と同じ品質で比較して採用、改善、停止を判断する評価フロー](/images/code-knowledge-graph-ai-review/05-evaluation-loop.png =900x)
*図 5：総トークン数、見逃し、誤検出、待ち時間、索引運用コストを同じタスクで比較します。*

### 5. 初期検索ではなく総コストを測る

採用判断では、回答が完成するまでの全工程を測定します。

- 追加参照を含む総トークン数
- 正答率
- 見逃し
- 誤検出
- 根拠のない断定
- p50／p95 の待ち時間
- インデックス構築・更新時間
- インデックス不整合からの復旧時間

## 採用基準

次の条件を満たした場合に限り、限定導入から対象拡大へ進みます。

- Baseline より見逃しが増えていない
- 総トークン数または待ち時間が実務上有意に改善した
- 根拠となるソースを追跡できる
- インデックスの鮮度を確認できる
- 外部通信と権限の範囲が承認されている
- 障害時に既存の検索手段へ戻せる
- 独立した Security Scanner とテストを維持している

## 最終判断

コード知識グラフは、AI コードレビューの探索順序を改善する手段として有用です。しかし、「トークン 2000 分の 1」や「推測を消す」という表現は、現在公開されている検証範囲を超えています。

検証用プロジェクトでは、**構造検索という設計思想は採用し、製品効果は `Serena` とグラフ製品 1 つによる読み取り限定の比較検証で判断する**のが妥当です。
